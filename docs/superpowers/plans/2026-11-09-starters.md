# Preflow Starters Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `preflow/starter` (a job board with pages, HTMX components and a REST API) and `preflow/starter-folio` (the same app with Folio added), together with the few framework pieces they need, as Preflow 0.63.0.

**Architecture:**
- **Framework first:** three small, general pieces land in the packages first:
  - `db:seed` boots the app;
  - a login redirect for HTML requests;
  - a page response for controllers.
- **Starters:** both live in `packages/starter` and `packages/starter-folio`.
  - Each is a standalone Composer project (`App\` → `app/`), installed and tested against the local packages by a new `bin/starter` script. Composer path repositories give the local packages a fake version that satisfies `^0.63`.
  - Starter 2 is a copy of starter 1 that changes only where Folio adds something.
  - Both starters keep their job queries and writes in two services (`JobSearch`, `JobWriter`) shared by the pages, the components and the API. Starter 2 swaps what is inside those services and leaves their callers alone.

**Tech Stack:** PHP 8.4+, Preflow 0.63 packages, Twig, HTMX (vendored by preflow/htmx), SQLite, PHPUnit 11, `league/commonmark` (Markdown in job descriptions).

**Spec:** `docs/superpowers/specs/2026-11-09-starters-design.md`. Facts gathered for this plan (file:line references) are summarised inline. The spec wins over this plan wherever they disagree, except for the rulings below.

## Rulings made while planning (the owner can overrule)

- **P1: framework release 0.63, starters require `^0.63`, not `^0.62`.** Checking the code found three general gaps the starters need. The framework rule says general pieces go into packages, so they ship as 0.63.0 together with the first release of both starters:
  - `db:seed` builds its own SQLite-only DataManager. It has no container, no validation, no `.env` and no `--class` option, so Folio's `Publisher` can't be used from a seed.
  - `AuthMiddleware` answers 401 and never redirects to a login page.
  - A controller can't render a page template the way file pages are rendered (assets, status 404). File pages can't 404 because component errors are swallowed by the error boundary.
- **P2: devtools moves to `require` (not `require-dev`) in both starters.** Production needs `php preflow migrate` and the `pages:work` cron. Folio already requires devtools.
- **P3: the API-only proof copies the app without `app/Components`, `app/pages` and `app/Controllers/Site`.** Page and component directories are hard-coded relative to the base path (`Application.php:916, 1622, 2479`), so a copy is the honest way to prove it. HTML controllers live under `app/Controllers/Site` and API controllers under `app/Controllers/Api`, and the README says to delete those three paths.
- **P4: job descriptions are Markdown in both starters.** The field is stored as `text` (Folio shows a monospace textarea), and the app renders it with `league/commonmark`: `html_input: escape`, `allow_unsafe_links: false`. Folio has no Markdown field type, and `richtext` would make the employer form and the API accept HTML.
- **P5: starter 2 drops `status` and `publishedAt` from `Job`.** Folio's publishing is the single source of truth (spec). Public reads go through `PublishedModels`. "Latest" sorts by the snapshot's `_published_at` column; if `orderBy('_published_at')` turns out not to work on the snapshot query, sort by a `postedOn` date field set on creation and record that as a ruling.
- **P6: guards.**
  - Starter 1 names its session guard `employers` (the default) and its token guard `token`.
  - Starter 2 adds a `staff` session guard as the default, because Folio's admin checks only the default guard.
  - Starter 2 marks `employers` with `'population' => 'members'`.
  - Employer routes use `App\Middleware\EmployerAuth`, which wraps `AuthMiddleware` for guard `employers`, in both starters, so the employer code doesn't change between them.
- **P7: no session for search.**
  - `auth.session.paths` is `['/employer']` in starter 1 and `['/employer', '/folio']` in starter 2.
  - `/--component` is left out on purpose: a visitor who searches must not get a session cookie, which would make every later page bypass the page cache.
- **P8: staff accounts in starter 2 are records (`App\Models\Staff`, table `staff`), not config users.**
  - The demo seed creates them; production creates the first one with the app command `preflow staff:create`.
  - Config users would put the demo passwords' hashes into a file that ships to production.
- **P9: account creation commands live in the starters, not the framework.**
  - Starter 1: `preflow employer:create <email> --company="<name>"`.
  - Starter 2 also has `preflow staff:create <email> --role=admin|editor`.
  - Both print a generated password once. They're project-specific (an employer needs a company).
- **P10: the skeleton's retirement takes two steps.**
  - In 0.63 the skeleton stays in the split one last time with `"abandoned": "preflow/starter"` in its composer.json and a README pointing to the starters. The owner also ticks "abandoned" on Packagist.
  - Removing `packages/skeleton` from the monorepo, the split and the root autoload is a ROADMAP item for the next release. None of the 5 sites depends on it.
- **P11: the page cache is off while `APP_DEBUG=1`, which is what `create-project` writes.** That is the framework's rule. The README shows how to watch the cache work (`APP_DEBUG=0`, `curl -I`), and the page cache test runs with debug off.
- **P12: the demo seed prints the demo logins.** `db:seed` runs last in `post-create-project-cmd`, so the logins appear at the end of `create-project`. Starter 1 has only a demo seed, because it needs no required data.
  - Starter 1 demo employer: `employer@example.com` / `demo-employer`.
  - Starter 2 adds `admin@example.com` / `demo-admin` and `editor@example.com` / `demo-editor`.

## Global Constraints

- PHP `>=8.4`. No Node, npm, bundler or build step in either starter.
- Both starters require released Preflow versions: every `preflow/*` is `^0.63`, never `dev-main`, and `minimum-stability` is `stable`.
- Install: `composer create-project preflow/starter myapp`, then `cd myapp && php preflow serve`. That gives a working, seeded app with no questions, on SQLite, with no database server. The same holds for `preflow/starter-folio`.
- `post-create-project-cmd`, in order:
  - copy `.env.example` to `.env`;
  - `@php preflow key:generate`;
  - `@php preflow migrate`;
  - `@php preflow db:seed`.
- `composer test` runs PHPUnit and passes on a fresh install.
- English only. i18n is wired as in the skeleton: `lang/en/*.php` and `t()`; `config/i18n.php` has `available => ['en']`.
- Seed companies are fictional. The seed is deterministic: ids are `md5('starter-<kind>-<n>')` and dates are fixed. Rerunning a seed upserts and never duplicates.
- The demo seeder refuses to run (it prints a reason and writes nothing) while `app.debug` is `0`.
- **Look:** plain CSS co-located in components with `{% apply css %}`; light and dark via `prefers-color-scheme`; works at 360 px width; no CSS framework.
- Job fields and values are the same in both starters, except where P5 says otherwise:
  - `employmentType` ∈ `full_time, part_time, contract, internship`;
  - `remote` ∈ `no, hybrid, full`;
  - `status` ∈ `draft, published` (starter 1 only).
- **JSON:** API keys are snake_case. The envelope is `Json::data($data, $meta)`, which gives `{"data", "meta"?}`. Errors come from the 0.62 JSON error renderer: `{"message"}`, and a 422 adds `errors: {field: [messages]}`.
- Paging: 12 per page in `/jobs` and `/api/jobs`.
- Framework code follows the monorepo's conventions. Each package README documents its new piece, and core and auth get upgrade notes.
- The starters' code is meant to be copied: no clever helpers, and comments explain why, not what.

## Review Focus

1. **Typing in the search box keeps focus, caret and text.** The result list swaps beneath it. A slow, older response never overwrites a newer one.
   - The form uses `hx-sync="this:replace"`, and its target is the results region, not the form.
   - Tested in Task 7: the rendered form carries `hx-sync="this:replace"` and an `hx-target` naming the results id.
2. **A visitor who searches gets no session cookie,** so the page cache keeps serving them.
   - Tested in Task 7: a `/--component/action` search response has no `Set-Cookie`.
3. **Hostile or odd filter values never cause a 500.** Examples: `?type=<script>`, `?remote[]=x`, `?page=-3`, `?page=999`, a 300-character `q`. They're normalised to defaults (q trimmed and cut to 100 characters). A page past the last one gives an empty list with correct meta.
   - Tested in Task 5 (`JobFilters`) and Task 9 (API).
4. **Fresh machine traps:**
   - A project path with a space breaks `preflow serve`: devtools passes the paths unquoted (`ServeCommand.php:37`). Fixed in Task 1, with a test.
   - Missing GD in starter 2 must not fail the seed: it imports the images without variants or skips them with a message (Task 12 test).
5. **Running `db:seed` twice** leaves the same row counts and no errors (Tasks 5 and 12).
