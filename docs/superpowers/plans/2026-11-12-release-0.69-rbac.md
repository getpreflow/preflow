# Release 0.69 — rbac without Folio Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** preflow/rbac works without Folio — stored roles, the staff-account lifecycle and their rules are a Folio-free core with commands; Folio carries rbac's admin as an adapter (spec D4; finding RBAC-1, STARTERS-2).

**Architecture:** rbac's core keeps RoleStore, the resolver, PermissionCoverage, the staff rules and a new `StaffAccounts` service, with its own install step and console commands; it no longer requires preflow/folio. The generic password-link logic Folio's `StaffPasswords` holds today moves to auth (`Preflow\Auth\Record\AccountLinks`), used by both Folio and rbac. Everything with `Preflow\Folio\` in rbac moves to `packages/folio/src/Rbac/` as Folio's built-in `rbac` extension (like members and codes). starter-folio switches to rbac.

**Tech Stack:** PHP 8.4, PHPUnit 11, the Preflow monorepo; site repos (smart-stack.works, holz-objekte.org, bggenius-preflow, languagecorner-preflow use rbac).

**Spec:** `docs/superpowers/specs/2026-11-12-package-audit-fixes-design.md` (D4, with the builder-check rulings). Evidence: `.superpowers/audit-2026-11-12/report-auth-rbac-members-notify.md` (RBAC-1), `report-folio-ui-starters.md` (STARTERS-2).

## Global Constraints

- Owner's rules: no workarounds; framework = abstractions only; Folio is the UI adapter; mails never mention Folio.
- After this release `packages/rbac/src` contains no `Preflow\Folio\` reference, and rbac's composer.json requires no preflow/folio and no preflow/devtools.
- Stored data keeps its names: table `rbac_role`, type keys `rbac_role` and `staff`, token purposes `folio.invite`/`folio.reset`, the Folio extension key `rbac` (sites' `config/folio/extensions.json` keep working), permission names.
- rbac is on when it is installed and its provider runs; Folio's extension switch only shows or hides the admin screens.
- Behaviour on the four rbac sites does not change; anything that would is a finding.
- Moved public classes keep a class alias for one release (`legacy-aliases.php` pattern); renamed console commands keep the old name as an alias for one release.
- Tests: package suites per task (`vendor/bin/phpunit --testsuite <Pkg>`), full suite at the release; never two test runs at once. No subagents inside tasks.

## Review Focus

1. A site upgraded from 0.68 (rbac extension installed, rbac_role rows, staff records) answers `can()` exactly as before on its first request. → Task 2 test `test_existing_install_keeps_answering`.
2. A fresh app without Folio: `rbac:install` then `staff:create` then sign-in through the staff guard works, and `can()` follows the stored role. → Task 3 test.
3. Delegation: a staff manager cannot grant a permission they don't hold, from Folio or from a command. → Task 3 tests.
4. The last active admin cannot be disabled or demoted, from Folio or a command. → Task 3 tests.
5. An invite link mailed from a command opens Folio's set-password page when Folio is installed; without a `StaffLinks` binding the command refuses with a clear message. → Task 3 tests.

### Task 2: rbac core without Folio — roles, install, resolver, role commands

**Files:**
- Modify: `packages/rbac/src/RbacResolver.php` (no `ExtensionState`), `RoleStore.php` (`installed(): bool`, `install(): void`), `RbacServiceProvider.php` (always on; core only), `PermissionCoverage.php`, `Messages.php`, `ConfigUsers.php`, `StaffManagers.php` (Folio-free)
- Create: `packages/rbac/migrations/…_create_rbac_role.php` or an `install()` that creates the table through the data layer's record-table sync (choose what preflow/codes and members do for their tables), `packages/rbac/src/Console/{InstallCommand,RolesCommand,RoleCommand,RoleDeleteCommand}.php`
- Create: `packages/rbac/models/rbac_role.json` (data keys only); the admin keys move to Folio's overlay in Task 4
- Test: rbac tests without a Folio app (a plain core app scaffold)

**Interfaces:**
- `RoleStore::installed(): bool` — the `rbac_role` table exists. Folio's extension install and `rbac:install` both make it true; sites upgraded from 0.68 are installed already.
- `RbacResolver::__construct(RoleStore $store, bool $debug = false)`; the "staff may do everything until installed" bootstrap reads `RoleStore::installed()`; log texts name `php preflow rbac:install`, not Folio.
- Console (registered via `extra.preflow.commands`):
  - `rbac:install` — creates the table if missing, seeds `staff/admin` ("Administrator", `*`) and `config/rbac.php` `seed` roles exactly as Folio's extension `seed()` does today (that seed moves here; Folio's extension calls it).
  - `rbac:roles [--population=staff]` — lists name, label, patterns.
  - `rbac:role <name> [--population=staff] [--label=…] [--grant=a,b] [--revoke=a,b]` — creates or changes a role; a granted name must be declared in auth's `PermissionRegistry` (or match a declared pattern, or be `*`), else exit 1 naming it.
  - `rbac:role:delete <name> [--population=staff]` — refuses while a staff record holds the role, and refuses deleting `admin` while it is the only role granting `*`.
- Ruling recorded: the permission list is auth's existing `PermissionRegistry`; Folio's `KnownPermissions` is the admin's "new permissions" notice state and stays in Folio.

### Task 3: StaffAccounts in rbac core and staff commands

- Create: `packages/rbac/models/staff.json` (data keys only)
- Test: rbac tests in a plain core app and with Folio

**Interfaces:**
- `StaffAccounts` (container service): `create(string $email, string $name, list<string> $roles, ?Authenticatable $actor = null): DynamicRecord`, `update(DynamicRecord $staff, array $changes, ?Authenticatable $actor = null): void`, `invite(DynamicRecord $staff): void`, `resetLink(DynamicRecord $staff): void`, `setPassword(DynamicRecord $staff, string $password): void`, `disable(DynamicRecord $staff, ?Authenticatable $actor = null): void` (epoch bump, remember rows revoked, links revoked), `enable(DynamicRecord $staff, ?Authenticatable $actor = null): void`, `find(string $email): ?DynamicRecord`. `$actor` null = the console (no delegation limit); with an actor, `PermissionCoverage` limits what can be granted.
- `interface StaffLinks { public function setPasswordUrl(string $token): string; }` — Folio binds it to its password page; without a binding `invite()`/`resetLink()` throw `StaffRefused::NO_LINK_PAGE` ("No page to set a password is configured; use staff:password, or install an admin that provides one.").
- The staff guard: `config/rbac.php` `guard`, else the guard Folio binds through a `StaffPopulation` value (Folio binds it from its `StaffGuard`), else auth's default guard.
- Commands: `staff:list`, `staff:create <email> --name=… --role=a,b` (prints nothing secret; follow with `staff:password` or `staff:invite`), `staff:password <email>` (reads the password twice from the terminal without echo, or from STDIN when not a TTY), `staff:invite <email>`, `staff:reset <email>`, `staff:disable <email>`, `staff:enable <email>`; refusals print the reason in words and exit 1.
